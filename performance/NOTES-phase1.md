# Phase 1 feasibility findings (local)

Folded into the README and deleted in Task 13.

## 1. Prepare (POST /prepare)

- First run FAILED: seed log "Initial seed finished with 101 errors", `Refit.ApiException 400` on `CreateBroker` for every user.
  Cause: the seed hard-codes `UseTls = true` (`InitialSeedBackgroundService`), `Modules:DataSource:Brokers:TestConnectionOnChange`
  defaults to true, so the API tests the connection with TLS against the plain-text Mosquitto on 1883
  (`MqttCommunicationException: Connection reset by peer` in the Rest log). Also the API (and later the broker client) validates the broker cert.
- Fix (commit "fix: local mosquitto TLS listener ..."): Mosquitto now has a TLS listener on 8883 next to plain 1883
  (`performance/local/mosquitto/mosquitto.conf`), certificate generated by `performance/local/mosquitto/generate-cert.sh`
  (CN/SAN `mqtt`, `localhost`; written to `docker/https/mqtt.{crt,key}`, git-ignored), mounted into the mqtt container.
  API containers get `SSL_CERT_FILE=${API_SSL_CERT_FILE}` (default `/etc/ssl/certs/ca-certificates.crt`, local `.env`: `/https/mqtt.crt`).
  `SEED_BROKER_PORT=8883`. After pulling these changes: run `generate-cert.sh`, add `API_SSL_CERT_FILE=/https/mqtt.crt` and `SEED_BROKER_PORT=8883` to `.env`,
  and re-run `up --no-start` (recreates containers).
- Second run: `Initial seed finished successfully.`; `senswave_seed` and `senswave_template` exist. Duration ~72 s for 100 users.
- Azure phase: the real broker must speak TLS with a publicly trusted cert (Let's Encrypt) and `API_SSL_CERT_FILE` stays default.

## 3. S5 without the DataSource worker

Activated `Rest` (otel false).
- Login `POST /api/v1/auth/login {"email","password"}` -> `{"tokenType":"Bearer","accessToken":"...","expiresIn":N,"refreshToken":"..."}` (ASP.NET Identity shape).
- `GET /api/v1/homes/current` -> `{"id":"<homeId>"}`. `GET /api/v1/homes` -> `{"items":[{"id","dataSourceId","name","icon","isOwner","location"}]}`.
  `dataSourceId` is the broker id.
- `GET /api/v1/devices/display?homeId=&page=1&size=30` -> `{"items":[{"id","roomId","name","icon","tile":{"type","value","configuration"},"presence":{...},"createdAtUtc","updatedAtUtc"}]}`;
  3 devices: `Empty Device`, `Movement Detector`, `Pico Controller` (tile type `Switch`).
- `GET /api/v1/devices/dashboards/display?deviceId=<deviceId>` (needs `deviceId`, NOT homeId; 400 empty body without it) -> `{"items":[{"id","name","icon","type"}]}` (Modes, Quick Actions).
- `GET /api/v1/devices/widgets/display?deviceId=` -> `{"items":[{"operation":{"id","name","type"},"widgets":[{"id","name","type","enabled"}]}]}`.
- `POST /api/v1/devices/{picoId}/tile/action {"value":true}` -> first attempt 400 `FailedToPublishMessage` / `FailedToSendMessage`:
  "Broker client does not exist" (`ClientDoesNotExist`). Seeding creates the broker but no running MQTT client; clients are started on demand.
  The API itself hosts the client (`DataSourcesModule` registers `AddBrokerClientServices`), so the worker is not needed, but each user's client must be started:
  `POST /api/v1/datasources/brokers/{brokerId}/clients {"username":"perf","password":"perf"}` -> 204 (brokerId = `dataSourceId` from `/homes`).
  (The seed's Refit route `/v1/datasources/clients/{id}` in `IClientsClient` does not match the endpoint route; not used by the seed.)
  After starting the client: tile action -> 200 with `tile.value=true`, and `mosquitto_sub -t 'perf/#'` shows `perf/controller/1 {"working":true}`.
  The client connected to Mosquitto over TLS (8883) with the `SSL_CERT_FILE` trust, so the fix above also covers runtime.
- Implication for Task 7/8: after every DB reset (template restore) no client is running, so the reset/verification step (or the load tool setup) must start the broker client
  for every simulated user (100 POSTs above) before S5, or S5 fails with 400. Clients are per API process and are lost on API restart.
